The 30-second pitch

Open with this, then let the interviewer choose where to go deeper.

I built a production system for a glass business. Customers enquire through the website. Partners create quotations with GST-correct pricing, an admin approves them, and won orders become projects that track payments, vendor costs and profit. It's a Node.js monolith with SQLite, running in Docker behind Caddy on AWS. I kept the design simple on purpose, because it has a handful of users and needs to be cheap and easy to run. It has 71 automated tests, nightly backups, and role-based access enforced on the server.

The problem

A shop with manual billing had no view of which quotations turned into orders, or which projects made money.

The users

Customers, partners who draft bills, and an admin who approves them. Mostly used on phones.

The goal

Accurate bills, a clear approval step, and honest numbers on profit and lost orders, at low running cost.

System architecture

One server, two containers. Only Caddy faces the internet, and the data sits outside the containers so a deployment can't remove it.

Request flow

What happens when the admin approves a bill. This is a good example because it touches every layer.

  1. The browser sends the requestPOST /api/bills/:id/approve over HTTPS, with an HttpOnly session cookie.
  2. Caddy receives itDecrypts it, adds the visitor's real IP, and forwards it over the private Docker network.
  3. Express checks identityThe cookie token is hashed with SHA-256 and looked up in sessions. The session must be unexpired and the user active.
  4. Express checks permissionrequireAdmin runs on the server, so hiding a button is never the only protection.
  5. One database transaction runsAssigns the next bill number, stores a snapshot of business details, and locks the bill. If this is a revision, it moves payments across too.
  6. The response returnsThe dashboard redraws and shows a confirmation.

How a bill is calculated

  1. Chargeable size = actual size + allowance (50 mm)
  2. Piece area = width × height, rounded to 4 decimals
  3. Amount = area × quantity × rate
  4. GST worked out per tax rate, split CGST/SGST, or IGST on the invoice
  5. Grand total rounded to the nearest rupee

Relationships: a user prepares and checks many bills. A bill has many payments and vendor payments. A bill can point to the bill it revises through revises_id, and to its replacement through superseded_by, which forms a version chain.

Database changes

The app adds any missing tables and columns when it starts. Changes are additive, so existing data stays intact, and tests cover upgrading an older database.

Rollback

Check out an earlier Git commit and rebuild the container. The data lives outside the container, and a backup is taken before every update.

Security in layers

No single control is trusted alone. Each layer limits the damage if another one fails.

NetworkFirewall allows 22, 80 and 443 only. The app has no public port.
TransportHTTPS everywhere, with HSTS and automatic certificates.
Passwordsscrypt with a unique salt, compared in constant time. Reset by an admin, never readable.
SessionsRandom 32-byte token, stored only as a hash. HttpOnly, Secure, SameSite=Lax cookie, 12-hour expiry.

Abuse limitsFailed sign-ins and enquiries are limited per visitor, with a hidden field to catch bots.

ContainersThe app runs as a non-root user. The deploy key is read-only.
Data on phonesThe service worker caches design files only, never bills or customer data.
IntegrityApproved bills are locked, invoice numbers are unique, and only an admin can delete money entries.

STAR stories

Real problems from this project, ready to tell.

Correcting locked bills without losing money records

SApproved bills are locked, but real mistakes still happen after payments are recorded.

TAllow corrections without editing history or losing payments.

AAdded revisions: an editable copy linked to the original. One transaction on approval moves payments and costs, then marks the old bill replaced.

RHistory stays intact, reports count only the latest version, and tests cover repeated revisions.

Matching real-world billing exactly

SThe bills had to match an existing supplier format to the paisa.

TWork out the hidden rounding rules from a sample invoice.

AReverse-engineered the sample, found area was rounded per piece, and wrote tests using its printed figures.

RThe system reproduced every figure on the sample bill, and tests now protect that logic.

A bug that only appeared behind the proxy

SBehind a proxy, every visitor looks like one IP address.

TStop one person's failed sign-ins from locking out everyone.

AConfigured trusted proxy handling, added a test with separate visitors, and later made successful sign-ins clear failed attempts.

RLimits now apply per visitor, and normal use no longer triggers lockouts.

Testing beyond automated checks

SA full review at four screen sizes passed, but a screenshot showed a squashed dropdown on phones.

TFind out why the check missed it, and stop it happening again.

ATraced it to a desktop rule leaking into the phone layout, fixed it, and added a new check for narrow controls.

RAll 92 page-and-size checks pass, and that type of bug now gets caught.

Known limits and how to scale

Being honest about weaknesses shows engineering judgement. Say what you would change, and when.

Known limits today

Single serverIf it fails, the site is down until restored
Deploy downtimeA brief outage on each update
Rate limits in memoryThey reset on restart and work on one server only
No CI yetTests are run by hand before pushing
No monitoringNothing alerts on downtime yet
Sydney regionSlower for India, and Mumbai is planned
No credit notesIssued invoices can't be reversed in the app

Scaling path, only when needed

  1. Now: add CI tests, uptime monitoring and off-site backups
  2. More traffic: larger server, CDN for images
  3. Several servers: move to managed PostgreSQL or MySQL, with shared rate limits in Redis
  4. High availability: load balancer with two app servers and rolling deploys
  5. Much larger: split only the parts that need it

Interview Q&A

Tap a question to see a short answer. Practise saying them in your own words.

Why SQLite in production?

The workload is a handful of users and low write volume, so a separate database server would add cost and failure points with no benefit. WAL mode allows reads during writes. I accepted the single-server limit and documented when I'd move to a client-server database.

How do you keep bill numbers unique and gap-free?

Numbers are assigned at approval inside a database transaction, not when a draft is created, so deleted drafts leave no gaps. Invoice numbers restart each financial year and have a unique index as a final guard.

How do you stop someone changing an approved bill?

The API rejects edits to approved bills, so it doesn't rely on the screen. Changes go through a revision, which keeps the original. A snapshot of business details is also stored at approval, so later settings changes can't alter old bills.

Why are bill lines stored as JSON?

They're always read together with the bill and must stay frozen after approval. JSON keeps that simple. The trade-off is harder line-level reporting, which I'd handle with a separate lines table if that need appeared.

How are passwords and sessions handled?

Passwords use scrypt with a unique salt and a constant-time comparison. Sessions are random tokens stored only as SHA-256 hashes, so a database leak doesn't expose live sessions. Cookies are HttpOnly, Secure and SameSite=Lax.

How do you protect against CSRF and XSS?

For CSRF, I rely on SameSite=Lax cookies and JSON API requests. A dedicated CSRF token would be a further hardening step. For XSS, all user text is escaped before rendering, and a test covers it on print pages. A Content Security Policy is a good next improvement.

What happens if the server dies?

Code is on GitHub and server snapshots are stored separately. I can restore a snapshot, or build a new server from the runbook, restore the database and point DNS at it. Data since the last backup could be lost, which is the main recovery risk today.

How do you handle database changes on deployment?

The app checks for missing tables and columns at startup and adds them. Changes are additive, so rollback stays possible, and there's a test that upgrades an older database. A versioned migration tool would be the next step as the schema grows.

What does the service worker do?

It makes the dashboard installable and shows an offline page. It deliberately avoids caching API responses, because financial data shouldn't stay on phones. It uses network-first for design files, so updates arrive immediately.

How is this tested?

71 automated tests cover calculations, permissions, workflows, migrations and backups, running against a real in-memory database. I also ran browser checks across 23 pages at four screen sizes, checking for errors, overflow and broken images, plus a manual screenshot review.

Why not Jenkins?

Jenkins needs its own server and ongoing upkeep, which isn't justified for one small app. GitHub Actions is the better next step: automatic tests on every push, then a manual deploy button.

What would you do differently?

I'd add CI and monitoring earlier, use a versioned migration tool from the start, and design revisions and tax invoices at the beginning, because they were added after real business needs came up.

What was the hardest part?

Modelling the real business correctly rather than the code itself. Things like an approved bill not meaning a won order, and corrections needing to preserve history, only became clear by following the real process.
